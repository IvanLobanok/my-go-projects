# Concurrent Connection Pool with Context Timeout 🔌⚡

Высокопроизводительный и безопасный пул соединений (Connection Pool) для условной базы данных (например, PostgreSQL или Redis) на языке Go. 

Проект решает критическую проблему бэкенд-разработки: исключает дорогостоящие накладные расходы на открытие и закрытие сетевых соединений при каждом запросе, заменяя их повторным использованием фиксированного пула ресурсов с поддержкой жестких тайм-аутов на ожидание.

## 🛠️ Архитектура и механизм пула

Пул спроектирован на базе стандартной библиотеки Go без использования сторонних зависимостей:
1. **Буферизированный канал как блокирующая очередь (`chan *Connection`)**: Пул инициализирует фиксированное количество коннектов (`maxConn`) и складывает их в канал. Канал в Go из коробки потокобезопасен и берет на себя всю логику блокировки потоков.
2. **Метод `Acquire(ctx)`**: Запрашивает соединение у пула. Вместо бесконечного ожидания метод мультиплексирует события через `select`. Если все коннекты заняты, горутина засыпает в ожидании. Если время ожидания превышает тайм-аут, переданный через `context.Context`, метод мгновенно прекращает ожидание и возвращает ошибку `context deadline exceeded`.
3. **Метод `Release(conn)`**: Возвращает отработавшее соединение обратно в буферизированный канал, мгновенно пробуждая следующую горутину, застрявшую в `Acquire`.

## 🧠 Примененные концепции Concurrency

* **Channel-Based Resource Pool**: Использование буферизированного канала в качестве пула объектов/семафора.
* **Context Timeout Control (`context.WithTimeout`)**: Ограничение времени ожидания ресурсов для предотвращения каскадных зависаний (cascading failures) во всей системе.
* **Graceful Resource Lifecycle**: Гарантированный возврат ресурсов в пул при любых исходах работы горутины.
* **Thread-Safety Without Manual Locks**: Элегантный отказ от явных мьютексов (`sync.Mutex`) в логике выдачи ресурсов — синхронизация полностью делегирована внутренним механизмам каналов Go.

## 💻 Сценарий стресс-теста в `main`

Для проверки надежности пула в коде смоделирована экстремальная нагрузка:
* Создается пул всего на **2 активных соединения**.
* Одновременно запускаются **5 рабочих горутин**, каждой из которых нужно поработать с базой данных в течение **600 мс**.
* Каждой горутине выделяется ровно **1 секунда (1000 мс) на ожидание** свободного коннекта.

**Магия таймингов на практике:**
1. **Воркеры 1 и 2** мгновенно захватывают коннекты №1 и №2 и уходят в работу на 600 мс.
2. **Воркеры 3, 4 и 5** блокируются в методе `Acquire`.
3. Через 600 мс первые воркеры освобождают коннекты. **Воркеры 3 и 4** тут же их перехватывают и уходят в работу еще на 600 мс.
4. **Воркер 5** продолжает ждать. Однако суммарное время ожидания для него составляет 600 мс (пока работали первые) + 600 мс (пока работают вторые) = **1200 мс**.
5. Поскольку 1200 мс > 1000 мс (лимит тайм-аута), контекст Воркера 5 отменяется, и он безопасно завершает работу, сообщив об ошибке, не вешая приложение.
